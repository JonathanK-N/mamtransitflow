# Transmission et réponse aux devis

Le dossier client utilise les factures de type `quote` existantes. « Envoyer le devis » passe par `commercial/<id>/send`, valide le client, son email et la date de validité dans le fuseau de l'entreprise, émet un numéro DEV avec le service existant, puis transmet le courriel par le transport existant (Resend ou SMTP). Un échec du transport annule la transaction : aucun statut Envoyé ni numéro ne reste enregistré.

Le lien ouvre `/devis#<jeton>` sans compte client. Le navigateur retire le fragment de sa barre d'adresse et conserve le jeton en mémoire ; une réouverture depuis le courriel permet de retrouver le devis. Le jeton aléatoire possède 256 bits d'entropie ; seule son empreinte SHA-256 est stockée. Le détail public contient uniquement les données du devis destinées au client. Le serveur ne transmet pas les notes internes, les identifiants internes, les autres devis, les finances globales, le personnel ni le GPS.

Les deux requêtes sont `POST public/quotes/preview` et `POST public/quotes/respond` avec le jeton dans le corps JSON. Elles n'utilisent aucune session ni cookie, sont limitées en fréquence et portent `no-store` et `no-referrer`. La consultation ne valide jamais le devis. Une réponse exige une confirmation explicite, prend les verrous entreprise et devis et utilise les transitions commerciales existantes. Une même décision répétée est idempotente ; une décision opposée retourne 409. L'audit conserve la décision sans jeton et les membres autorisés reçoivent la notification existante. La conversion en commande reste une action interne.

Le lien expire à minuit après la date de validité dans le fuseau de l'entreprise. L'archivage du client le rend inaccessible. « Renvoyer le devis » remplace le jeton après un envoi réussi, tandis qu'un échec conserve le lien précédent. « Retirer le lien client » le fait expirer immédiatement sans modifier la décision commerciale.

`QuoteLink` est une table technique liée au devis existant, pas un nouveau système de devis. La migration 0025 ajoute une référence composite PostgreSQL pour empêcher un rattachement à une autre entreprise. Les tests backend simulent le transport mail et vérifient les statuts, le détail minimal, l'expiration, la révocation, l'idempotence, les notifications, les permissions et les limites. Les tests navigateur vérifient la confirmation et l'expiration sur cinq profils ; ils simulent les réponses publiques et ne constituent pas une preuve d'arrivée dans une boîte email réelle.

Limite du transport synchrone existant : une panne du processus après l'acceptation par le fournisseur et avant la validation de la transaction peut produire un courriel dont le lien est inutilisable. Le renvoi depuis le dossier fournit un nouveau lien. La preuve de réception dépend du fournisseur et du destinataire ; un retour accepté par le transport ne prouve pas une lecture.

La recette CRM complète utilise maintenant un récepteur SMTP local sur 127.0.0.1:8025, limité aux destinataires `.test`. Le serveur de test n'effectue aucune livraison extérieure. La recette lit le courriel réellement reçu par ce récepteur, ouvre son lien dans une session client sans compte et confirme l'acceptation avant de créer la commande. Le récepteur repose sur [le contrôleur et les handlers documentés d'aiosmtpd](https://aiosmtpd.aio-libs.org/en/latest/controller.html). Il est une dépendance de développement, absente de l'image de production. La recette refuse de démarrer sur une URL distante ou sans boîte SMTP de test.
