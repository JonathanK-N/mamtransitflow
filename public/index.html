Lire le modèle relationnel de TransitFlow

Le modèle relationnel logique (MRL) décrit les tables, leurs colonnes et les liens qui organisent les données. Cette vue est issue des migrations du code livré, sans connexion à la base de production et sans contenu utilisateur.

Version de référence

Les clés et les cardinalités

PK identifie une ligne de manière unique. FK référence une clé d’une autre table. UQ impose une valeur unique. NULL signifie qu’une colonne peut rester absente dans la base.

Le trait part de la table qui contient la clé étrangère et pointe vers la table référencée. À son extrémité cible, 1 signifie une référence obligatoire et 0..1 une référence facultative. Du côté de la table dépendante, 0..N autorise plusieurs lignes et 0..1 indique une référence unique. Ces cardinalités décrivent les contraintes structurelles, pas toutes les règles métier.

L’isolation des entreprises

La plupart des tables ERP contiennent organization_id. Les contraintes composites PostgreSQL vérifient aussi le couple (organization_id, référence) afin d’empêcher une mission, un document ou une autre fiche de pointer vers une fiche appartenant à une autre entreprise. Les traits violets discontinus identifient ces relations. Le détail présente le SQL de la contrainte.

Les liens directs vers l’entreprise et l’utilisateur sont masqués dans le diagramme par défaut pour préserver sa lisibilité. Activez « Liens d’identité » pour les voir. Ils restent toujours présents dans le dictionnaire et le détail des tables.

ERP actuel, système et historique

Le filtre « ERP actuel » présente les tables erp_*. « Identité et système » regroupe les comptes, permissions, sessions et migrations. Les anciennes applications restent visibles sous « Tables historiques ». Leur présence dans le schéma ne signifie pas que leurs anciennes routes sont actives dans le SaaS.

Les champs JSON et les fichiers

Un champ jsonb conserve une structure définie par l’application, pas un ensemble de tables SQL supplémentaires. Les fichiers sont stockés séparément, et les colonnes de fichier conservent leur chemin. Ce diagramme n’ouvre et ne télécharge aucun document métier.

Suppression et unicité

Les indications CASCADE, PROTECT, SET_NULL et autres dans le détail sont les politiques du modèle Django. Elles ne sont pas présentées comme des clauses SQL ON DELETE. Les contraintes nommées, les index explicites et les unicités sont listés sous chaque table.

Portée et traçabilité

    Les modules locaux non encore livrés, notamment la messagerie et la nouvelle paie configurable, ne sont pas confondus avec cette version de référence. Ce fichier décrit le schéma attendu par les migrations, pas une introspection du catalogue physique de Railway.

    Explorer le schéma

    1. Choisissez une table dans la liste ou recherchez un nom de champ.

    2. « Liens de la table » affiche ses voisins directs. « Vue globale » affiche les tables qui correspondent aux filtres.

    3. Glissez le diagramme pour vous déplacer. Utilisez la molette, les boutons + / − et « Cadrer » pour ajuster la vue.

    4. Le panneau de droite détaille toutes les colonnes, relations et contraintes. Les liens de table permettent de naviguer dans le modèle.

    5. Exportez la vue en SVG ou le schéma en JSON, DBML et MRL texte. Tout fonctionne localement, hors connexion.
